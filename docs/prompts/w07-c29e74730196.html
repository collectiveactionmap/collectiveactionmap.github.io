Abstract mechanism detection prompt

ROLE You are coding records already retained in the review. Your task is to identify which collective-action mechanism types, if any, are supported by the publication's supplied title, abstract and keywords. Use the accompanying ostara_w07_mechanism_ontology_v4.csv as the controlled vocabulary. The ontology has collective_action_type > high_level_mechanism > fine_level_mechanism hierarchy; each mechanism has a definition. Screening eligibility has already been established; do not repeat inclusion screening.

DEFINITIONS A collective action mechanism [hereafter referred to as ‘mechanism’] is defined as a specific system, process, instrument or intervention that operationalises collective action and aims to align the actions of actors in pursuit of a specific function, purpose or common goal. Collective action mechanisms can be grouped into categories, which refer to the specific function or purpose of the collective and aims to organise the different types and reasons for collective action, such that a category consists of more than one mechanism.

A mechanism which conforms to the above definition qualifies as a collective action mechanism even if it is not explicitly called a “collective action mechanism” or a “mechanism”.

PROVISIONAL CODING RULES - The controlled ontology is frozen at 30 codes for this round. Do not invent codes or add types during coding. - When no code fits, distinguish a genuinely novel collective sustainability mechanism (ontology_gap=true), insufficient abstract information (coding_status=insufficient_information), and a record with no supported mechanism (coding_status=no_supported_mechanism). Explain the reasoning in coding_notes. - A prospective or proposed mechanism can be coded when its operational arrangement is identifiable, but mark implementation_status=proposed. Distinguish implemented, proposed, mentioned_only and unclear for each assigned mechanism. A failed or discontinued implemented mechanism remains implemented. Whether proposed mechanisms should enter the final ontology is a pending team decision. - Ontology gaps are candidate proposals only, saved in a separate registry pending consolidated team review after the full evidence base has been assessed.

CODING PRINCIPLES 1. Code the mechanism: HOW distinct actors deliberately coordinate actions, commitments, governance, markets, finance, monitoring or resources towards a shared sustainability objective. Do not confuse a named organisation, coalition, initiative, case, certification label, sector or goal with a mechanism. 2. Apply zero, one or multiple mechanism_ids if EACH is independently evidenced. Assign each mechanism_id at most once per publication, even if multiple initiatives illustrate it. Do not infer that every mechanism mentioned in an ontology's source example applies to the publication. 3. For each selected mechanism, give short evidence grounded in the supplied title, abstract or keywords, with a short verbatim supporting text excerpt and its source (title, abstract or keywords). Only label text as a quotation when verbatim. Do not invent a quotation, initiative, actors or outcome. 4. A generic mention of partnership, initiative, stakeholders, joint authorship or a shared problem is insufficient to identify a mechanism. The record must support an identifiable operational arrangement or action. If a specific code is plausible but unclear, mark confidence=low and implementation_status=unclear, explaining why. If no mechanism can be identified because information is missing or ambiguous, use coding_status=insufficient_information rather than no_supported_mechanism. 5. Missing abstract: title-only coding is permissible only for unambiguous mechanisms; otherwise mark information insufficient. 6. No match: if the supplied record describes an identifiable mechanism but none of the existing definitions fits, do not force a match. Set ontology_gap=true, describe the distinct mechanism, identify the closest existing mechanism_id (or null if none), and explain why that definition is insufficient. A new initiative, sector, organisation or implementation of an existing mechanism is not by itself an ontology gap. If information is too vague, set ontology_gap=false and coding_status=insufficient_information; if the record supports no identifiable mechanism despite sufficient information, use coding_status=no_supported_mechanism. 7. This is publication-level coding, NOT an initiative register. Never create duplicate rows for different named examples. Distinct initiatives may be identified later in a separate case extraction phase. 8. A failed mechanism remains codable.

INPUTS PER RECORD record_id, title, abstract, keywords (if available); mechanism ontology CSV with mechanism IDs and definitions.

OUTPUT Return exactly one JSON object per record with the following structure. Produce valid JSON only; no surrounding prose. { "record_id": "exact input ID", "coding_status": "coded | insufficient_information | no_supported_mechanism", "mechanisms": [ {"mechanism_id": "M1.1.1", "evidence": "Short record-grounded description", "evidence_excerpt": "Verbatim short text from title, abstract or keywords", "evidence_source": "title | abstract | keywords", "confidence": "high | medium | low", "implementation_status": "implemented | proposed | mentioned_only | unclear"} ], "ontology_gap": false, "proposed_new_mechanism": null, "ontology_gap_reason": null, "closest_existing_mechanism_id": null, "novel_terminology": ["distinctive, actually used terms worth testing in later searches"], "coding_notes": "Short explanation of uncertain or borderline cases" }

If ontology_gap is true, proposed_new_mechanism must be a concise, sector-neutral mechanism description, ontology_gap_reason must explain the mismatch, and closest_existing_mechanism_id must identify the nearest existing code or be null if none is appropriate. If ontology_gap is false, all three fields must be null. Use coding_status=coded when at least one mechanism is coded or a supported ontology gap is identified; otherwise use insufficient_information or no_supported_mechanism according to the evidence. Arrays can be empty. Do not assign an invented mechanism_id. Do not add codes that are not in the supplied ontology.

QUALITY CHECK BEFORE RESPONDING - Every mechanism_id exists in the supplied ontology. - Each assigned code has record-specific evidence. - Multiple mechanisms are preserved if supported. - Existing types are not forced onto genuinely novel mechanisms.

OSTARA W09 FULL-TEXT MECHANISM INVENTORY + INDEPENDENT CASE-PRESENCE SWEEP (v2)

PURPOSE Evaluate all approved mechanisms throughout the complete supplied full text. Independently perform a lightweight case-presence sweep to route later extraction. The mechanism inventory must NOT depend on prior case detection, W09 case extraction, eligible case IDs, or the outcome of the case-presence sweep. Return one JSON object only.

MECHANISM INVENTORY Evaluate EVERY mechanism_id in approved_ontology exactly once, including those absent from the abstract. Classify its status: - implemented_case: the full text directly establishes that the mechanism was actually used or implemented in real-world collective action, irrespective of whether a case record or ID was extracted separately - mentioned_only: substantive discussion or description, without direct support of actual implementation in the supplied text - proposed_only: a recommendation, conceptual approach, plan, or hypothetical future use, not demonstrated as implemented - not_identified: no support for the mechanism in the full text - unclear: relevant text is too ambiguous for a supported status

The status label implemented_case is retained for compatibility with the approved downstream ontology schema. It does NOT require a case ID, an extracted case, or agreement with case-presence status. NEVER assign a case ID, create a case link, or modify mechanism status because a case ID is absent. A mechanism can be implemented even where no distinct eligible case can be extracted.

For every status except not_identified, provide a concise verbatim source_quote, an exact source_anchor ([PAGE n], [SECTION n], or [TEXT BLOCK n] exactly as provided), and a reason; if evidence is absent, classify not_identified rather than inventing quotations. Use exact approved mechanism IDs only.

NOVELTY REVIEW For every W07 novelty proposal in w07_abstract_novelty, explicitly classify full-text support as confirmed_novel, refined_novel, covered_by_existing, rejected, or uncertain. For a covered_by_existing decision, identify the corresponding approved mechanism ID. Include a source quotation and anchor when textual support is claimed. Do not automatically adopt new mechanisms into the approved ontology.

Independently propose truly new mechanisms in new_novelty only where they are substantively supported by the full text and not already covered by any approved mechanism. These may be observed/implemented or clearly proposed; specify support_status as implemented, proposed, or unclear, explain novelty relative to closest codes, and include exact quotation and source anchor. Case identification and case IDs are NOT prerequisites. Do not duplicate a proposal already addressed in abstract_novelty_validation.

This is inventory and candidate ontology assessment, not effectiveness or impact evaluation. Do not extract case-level details or general insights here.

FULL-TEXT CASE PRESENCE SWEEP Independently assess whether the entire full text identifies any real-world collective-action arrangement meeting the exact supplied w08_case_inclusion_criteria. In particular, an eligible distinguishable arrangement requires two or more actors, groups, or organisations deliberately coordinating activities, decisions, resources, commitments or governance towards an environmental or social sustainability objective. Mere institutional names, ordinary commercial transactions, research activity, aspirational collaboration, or vague references to partnership are insufficient. Explicitly described proposed arrangements may qualify as candidates if distinguishable, but must not be presented as implemented.

This assessment is separate from mechanism inventory. Use the W08 criteria in full, do not broaden them, and independently check the complete full text regardless of abstract classification. If criteria are missing, classify unclear and state why.

case_status: - case_present: one or more distinguishable arrangements sufficiently meet the supplied criteria. - no_case: no qualifying identifiable arrangement is found in the supplied full text. - unclear: evidence is ambiguous or too incomplete to determine case presence.

Return candidate_case_count as integer >=1 for case_present, 0 for no_case, and null for unclear. candidate_cases must have exactly candidate_case_count entries for case_present; [] for no_case; for unclear may include genuine ambiguous candidates. Candidates are provisional, NOT W09 case IDs. For each candidate provide a short descriptive label, case_description, verbatim source_quote, exact source_anchor and eligibility_reason.

Include assessment_reason. Compare to final_w08_case_status if provided: agrees, disagrees, not_comparable (W08 unclear), or not_provided (missing). Set review_required true if case_status is unclear or w08_comparison is disagrees. The sweep never changes W08 adjudications; flagged differences require review before routing to either downstream case or insights extraction.

QUOTE AND ANCHOR INTEGRITY Every nonempty source_quote must be an exact continuous substring of the supplied fulltext (whitespace normalisation only if the text was normalised upstream). Use only existing anchor markers. Never fabricate quotations or page numbers for XML/JSON. A negative case assessment needs reasoning, not a fabricated absence quote.

OUTPUT JSON (all arrays/objects required; return actual values, not pipe-separated choices): { "record_id":"input record ID", "case_presence_assessment":{ "case_status":"case_present", "candidate_case_count":1, "candidate_cases":[{"candidate_label":"","case_description":"","source_quote":"","source_anchor":"","eligibility_reason":""}], "assessment_reason":"", "w08_comparison":"not_provided", "review_required":false }, "mechanism_inventory":[ {"mechanism_id":"","status":"not_identified","source_quote":"","source_anchor":"","reason":""} ], "abstract_novelty_validation":[ {"abstract_candidate_id":"","original_proposal":"","status":"uncertain", "closest_approved_mechanism_id":"","revised_label":"","revised_definition":"", "source_quote":"","source_anchor":"","reason":""} ], "new_novelty":[ {"proposed_label":"","working_definition":"","support_status":"proposed", "closest_approved_mechanism_id":"","source_quote":"","source_anchor":"","reason":""} ] }

If there is no W07 novelty proposal return abstract_novelty_validation: []; if no justified novel mechanism return new_novelty: []. Do not output any case_ids field anywhere. Keep the exact case_presence_assessment object even when status is no_case.
